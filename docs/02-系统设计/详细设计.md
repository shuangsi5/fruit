### 3.1 下单支付流程类交互

前端提交订单 → `OrderController` 校验 → `OrderServiceImpl.createOrder`（事务内：校验商品状态与库存 → 计算金额 → 生成订单与明细 → `InventoryServiceImpl.lockStock` 预占 → 写 `inventory_log`）→ 返回待支付订单。
用户支付 → `OrderServiceImpl.pay`（校验状态 → 生成 `payment_record` → 模拟支付成功 → 扣减锁定库存 → 状态 `0→1` → 写物流待发货）。
详见 `docs/uml/时序图-下单支付.puml`。

### 3.2 库存预警流程类交互

`WarningScanJob` 定时触发 → `WarningEngine.evaluate` 读取商品、库存、近 7 日销量 → 计算临期等级、损耗等级、库存等级 → 取最大值写入 `inventory.warning_level` → 商家端 `GET /api/merchant/inventory/warnings` 查询结果并展示。
详见 `docs/uml/时序图-库存预警.puml`。

## 4. 领域模型与状态机

### 4.1 订单状态机

状态流转由服务端强制校验，禁止跨状态跃迁：

```
待支付(0) --支付成功--> 待发货(1)
待支付(0) --取消/超时--> 已取消(4)
待发货(1) --发货--> 运输中(2)
待发货(1) --取消(商家同意)--> 已取消(4)
运输中(2) --确认收货/超时--> 已完成(3)
已完成(3) --申请售后--> 售后中(5)
售后中(5) --售后处理完成--> 已完成(3)
```

详见 `docs/uml/状态图-订单.puml`。

### 4.2 关键业务规则

1. **价格服务端计算**：订单金额由商品当前 `price × quantity` 累加，忽略前端传入金额。
2. **库存预占**：下单锁库存，支付扣库存，取消回补库存，全程写 `inventory_log`。
3. **状态校验**：每次状态变更前校验当前状态，非法跃迁抛 `10003`。
4. **数据权限**：商家仅操作 `merchant_id` 匹配的数据，用户仅操作本人数据。
5. **时间约束**：支付超时 30 分钟自动关单；售后限完成后 7 天内申请。

## 5. 推荐引擎详细设计

采用**混合推荐**：购买频次 + User-Based 协同过滤 + 热销兜底，输出 TopN 商品。

### 5.1 输入数据

- 用户购买记录：来自 `orders`（`status IN (1,2,3)`，近 180 天）与 `order_item`。
- 协同过滤矩阵：所有用户的 `user × product` 购买次数。
- 热销数据：近 30 天各商品销量 `sales_count`。
- 商品状态：`status=1`、`stock>0`、剩余保质期 `>1` 天。

### 5.2 购买频次得分

对用户 u 购买商品 i 的次数 `c(u,i)`，频次得分归一化：

```
freq(u, i) = c(u, i) / max_{j∈P(u)} c(u, j)
```

其中 `P(u)` 为用户 u 购买过的商品集合。

### 5.3 User-Based 协同过滤

评分采用 `r(u,i) = 1 + ln(c(u,i))`（抑制高频偏差）。用户 u 与 v 的余弦相似度：

```
sim(u, v) = (Σ_{i∈I(u)∩I(v)} r(u,i)·r(v,i)) / ( sqrt(Σ_{i∈I(u)} r(u,i)²) · sqrt(Σ_{i∈I(v)} r(v,i)²) )
```

取相似度 Top-K（K=20）且 `sim>0` 的用户，计算目标用户对候选商品 i 的协同得分：

```
cf(u, i) = Σ_{v∈N(u)} sim(u,v)·r(v,i) / Σ_{v∈N(u)} sim(u,v)
```

其中 `N(u)` 为相似用户集合，且 v 购买过 i 而 u 未购买过 i 的商品作为候选。

### 5.4 热销得分

近 30 天销量 `s(i)` 归一化：

```
hot(i) = s(i) / max_{j∈All} s(j)
```

### 5.5 混合排序公式

对候选商品 i，综合得分：

```
score(u, i) = w1 · freq(u,i) + w2 · cf_norm(u,i) + w3 · hot(i)
```

默认权重 `w1=0.5, w2=0.3, w3=0.2`（可配置），`cf_norm` 为 `cf` 的极差归一化结果。按 `score` 降序取 TopN（N 默认 10，最大 50）。

### 5.6 冷启动与兜底

- 无购买记录的新用户（`P(u)` 为空）：跳过频次与 CF，直接按 `hot(i)` 降序返回热销榜。
- 候选不足：用热销榜补足至 N 个。
- 返回 `algorithm` 字段标识实际算法（`FREQUENCY`/`CF`/`MIXED`/`HOT`），`reason` 字段给出推荐理由。

### 5.7 伪代码

```
FUNCTION recommend(user, scene, N):
    bought = queryPurchases(user, last180Days)
    IF bought IS EMPTY:
        RETURN topHot(N) WITH algorithm='HOT'          // 冷启动兜底
    freq = computeFrequency(bought)                    // 5.2
    simUsers = topKSimilarUsers(user, K=20)            // 5.3
    cf = computeCF(user, simUsers)                     // 5.3
    cfNorm = minMaxNormalize(cf)
    hot = computeHot(last30Days)                       // 5.4
    candidates = filterOnShelfInStockNotExpiring()     // 5.1 过滤
    FOR EACH i IN candidates:
        score[i] = 0.5*freq[i] + 0.3*cfNorm[i] + 0.2*hot[i]
    top = sortByScoreDesc(score)[:N]
    saveRecommendationLog(user, top, score, source='MIXED')
    cache(user, scene, top, TTL=30min)
    RETURN top
```

### 5.8 缓存与时效

- 缓存键：`reco:{userId}:{scene}`，TTL 30 分钟。
- 失效：订单完成/售后变更时清除该用户推荐缓存；每日凌晨全量重算热销榜。
- 教学环境若无 Redis，可用 Caffeine 本地缓存降级。

## 6. 预警引擎详细设计

基于**保质期与销量**计算临期、损耗与库存不足预警，输出等级 0-3。

### 6.1 输入数据

- 商品：`production_date`、`shelf_life_days`、`status`、`price`。
- 库存：`stock`、`safety_stock`。
- 销量：近 7 日该商品销售件数 `q7`。

### 6.2 临期预警

剩余保质期天数：

```
remainingDays = shelf_life_days - DATEDIFF(CURDATE(), production_date)
```

| remainingDays | 等级 | 含义 |
|---------------|------|------|
| > 30 | 0 | 正常 NORMAL |
| (7, 30] | 1 | 注意 NOTICE |
| (3, 7] | 2 | 警告 WARNING |
| ≤ 3 | 3 | 严重 CRITICAL |

### 6.3 损耗预警

日均销量与临期前预计可销量：

```
avgDailySales = q7 / 7
predictedSales = avgDailySales × max(remainingDays, 0)
lossRisk = IF remainingDays <= 0 THEN 1 ELSE max(0, (stock - predictedSales) / stock)
```

| lossRisk | 等级 | 含义 |
|----------|------|------|
| ≤ 0.2 | 0 | 正常 |
| (0.2, 0.4] | 1 | 注意 |
| (0.4, 0.7] | 2 | 警告 |
| > 0.7 | 3 | 严重 |

### 6.4 库存不足预警

```
IF stock <= 0        THEN level = 3
ELSE IF stock <= safety_stock THEN level = 2
ELSE level = 0
```

### 6.5 综合等级

```
warning_level = MAX(临期等级, 损耗等级, 库存等级)
```

`warningType` 取导致最高等级的类型（`EXPIRING`/`LOSS`/`LOW_STOCK`），`suggestion` 按类型与等级生成文案（如「剩余 5 天保质期，建议促销清仓」）。

### 6.6 伪代码

```
FUNCTION evaluate(product, inventory, q7):
    rd = product.shelfLifeDays - daysBetween(today, product.productionDate)
    expiringLevel = levelByRemainingDays(rd)               // 6.2
    avg = q7 / 7
    predicted = avg * max(rd, 0)
    lossRisk = rd <= 0 ? 1 : max(0, (inventory.stock - predicted) / inventory.stock)
    lossLevel = levelByLossRisk(lossRisk)                  // 6.3
    stockLevel = inventory.stock <= 0 ? 3
               : inventory.stock <= inventory.safetyStock ? 2 : 0   // 6.4
    level = max(expiringLevel, lossLevel, stockLevel)
    type = argMaxType(expiringLevel, lossLevel, stockLevel)
    RETURN { level, type, remainingDays: rd, avgDailySales: avg, lossRisk, suggestion: buildSuggestion(type, level) }
```

### 6.7 调度与落库

- `WarningScanJob` 每日 02:00 扫描 `status=1` 且 `deleted=0` 的商品，逐条调用 `evaluate`，更新 `inventory.warning_level`。
- 商家端查询预警接口实时调用引擎，保证数据新鲜；定时任务结果用于历史趋势与报表。
- 阈值与权重通过配置项注入，便于课程演示调参。

## 7. 异常处理规范

### 7.1 业务异常

统一使用 `BizException`（携带 `ResultCode`），在 service 层抛出：

```
throw new BizException(ResultCode.STOCK_NOT_ENOUGH);   // 10001
```

### 7.2 全局处理

`GlobalExceptionHandler` 统一捕获并封装为 `Result`：

| 异常类型 | 映射 code | 说明 |
|----------|-----------|------|
| `BizException` | 对应业务码 | 业务规则不满足 |
| `MethodArgumentNotValidException` | 40001 | 参数校验失败，message 含字段提示 |
| `HttpMessageNotReadableException` | 40002 | JSON 格式错误 |
| `AuthenticationException` | 40101/40102 | 未登录/Token 无效 |
| `AccessDeniedException` | 40301 | 权限不足 |
| `DuplicateKeyException` | 40901 | 唯一键冲突 |
| 其他 `Exception` | 50001 | 系统错误，记录完整堆栈 |

### 7.3 事务与回滚

- 下单、支付、发货、售后处理等使用 `@Transactional`，运行时异常自动回滚。
- 乐观锁冲突（`version` 不匹配）抛 `40902`，由前端提示重试。

## 8. 日志规范

- 框架：SLF4J + Logback；生产日志级别 `INFO`，开发 `DEBUG`。
- 格式：`时间 级别 [线程] 类名 - 消息`，异常打印堆栈。
- 关键节点（必须记录）：登录成功/失败、下单、支付、发货、审核、售后处理、预警扫描、权限拒绝。
- 敏感信息脱敏：密码、手机号（中间四位）、Token、身份证/营业执照号不打印明文。
- 链路标识：建议用 TraceId（MDC）串联一次请求的日志，便于排查。
